# GreenField Evaluator: unified refactor plan

Nov 3, 2026 · @Aaron

## Summary

The three reviews collapse into **30 work items in 6 waves**, merged from 52 raw findings, 8 of which were reported by two reviews. Security goes first, because it changes the core scorer, portfolio, ledger and dashboard server that the UX and UI work then builds on. The unified `greenfield` CLI and the README rewrite go late, so the docs describe the final commands once instead of being rewritten twice.

Analogy: this is a house renovation. Security is the wiring and locks, the UI is the drywall and fixtures, and the README is the paint. You can do them in any order, but painting before rewiring means painting twice.

Sources: [security review](https://claude.ai/artifact/3aFGtvNf5GvjJBfzR2vPGk) (H1 to L3), [UX review](https://claude.ai/artifact/RRWYd2ZABGbPzWzH7Lczu9) (UX1 to UX15 plus P2 polish), [UI review](https://claude.ai/artifact/1kMZYDa3wuNY9hZfdqFows) (U1 to U18) and its [Mission Control mockup](https://claude.ai/artifact/SEwPzhUYjF2hcydytzQzY8). The schema\_version scoring bypass is already fixed in `score_project.py` and is out of scope. No code was changed for this plan.

## Conflicts and how they are resolved

Six places where the reviews pulled in different directions or would have broken each other's work.

| Conflict | Resolution |
| --- | --- |
| **The new Decision panel would repeat the H3 exploit.** UI's `/api/decision` reads `decision.json` as written, which is exactly what security showed can be forged. It also builds a path from a run slug. | `/api/decision` reuses W8's re-scoring function and shows the recomputed verdict, flagging any mismatch. The path goes through `resolve_inside()` (W6). So W18 waits for W6, W8 and W9. |
| **Scorer output format.** UI and UX want human text by default; agents and the portfolio parse JSON. | Text only when stdout is a TTY. Piped output stays JSON, and SKILL.md passes `--json` explicitly so agents never depend on TTY detection. `decision.json` gains `headline`, keeps `memo_label` for one release. |
| **CSP and inline script.** UI said security's CSP changes should land first and might force JS into a separate file. | Security's review found no CSP change needed (current policy allows inline script, served from loopback). The dashboard stays one self-contained HTML file. Tightening `script-src` is optional later work, not a blocker. |
| **Self-attestation hook vs new CLI.** Security's hook blocks `gf_ledger.py record --attester`; the CLI renames it to `greenfield ledger record`. | The TTY and HMAC parts of H2 land in wave 1 and don't care about command names. The hook rule moves to W27 and matches both the old script and the new subcommand. W5 already removes Bash from research agents, which covers most of the risk until then. |
| **README rewritten twice.** UX put the README rewrite in its phase 1, but its phase 2 renames every command. | Fix only the false statements now (W17). The full quickstart (W28) waits until the CLI exists, so it documents final commands. |
| **Agent files regenerated three times.** H1 (tool limits), ROLES names and the new CLI all change the generated agents. | All three go through `make_agents.py`, so regeneration is cheap. W4 lands first so H1 uses final names; W27 regenerates once more for CLI paths and adds a freshness test. |

Smaller overlaps simply merged: the `.gitignore` gap (security L1 and UX4), shipped `.pyc` files (L3 and UX packaging), portfolio escaping (L2 and U16), error wording (M3 and UX9), CLI help (UX15 and U11).

## Waves, in dependency order

Each wave is shippable on its own and ends with the full test suite green. Inside a wave, items touching different files can run in parallel. Rough total: 5 to 6 working days.

1. **Wave 0: foundation, no behavior change (half a day).** W1 shared helpers, W2 packaging hygiene, W3 CI, W4 `ROLES` table. Everything later imports W1 and W4, so they go first. Gate: tests pass, installed copy has no `.pyc`.
2. **Wave 1: close the trust exploits (1 day).** W5 agent tool limits, W6 path confinement, W7 never-throwing validator, W8 portfolio re-scoring, W9 dashboard Host check, W10 hook platform flag, W11 attestation (if approved). Order inside: W7 before W8, because portfolio re-scoring calls `validate()`. Gate: a regression test reproduces each exploit from the security review and now fails to reach `PROCEED_TO_BOUNDED_PILOT`.
3. **Wave 2: output and guardrails (1 day).** W12 scorer verdict and text output, W13 portfolio labels and escaping, W14 active-run guard, W15 file permissions and `.gitignore`, W16 fetcher hardening, W17 README factual fixes. W12 and W13 wait for W8 because they change fields the portfolio reads. Gate: snapshot tests of scorer text for the template and a filled fixture.
4. **Wave 3: dashboard (1 to 1.5 days).** W18 Decision panel, W19 render diffing, W20 status correctness, W21 polish. W18 waits for W6, W8, W9 and W12. W20 reads role names from W4 via `/api/state`. Follow the [mockup](https://claude.ai/artifact/SEwPzhUYjF2hcydytzQzY8). Gate: Playwright smoke test keeps focus and feed scroll across two refreshes.
5. **Wave 4: one CLI (1.5 to 2 days).** W22 dispatcher and `pyproject.toml`, W23 doctor and profiles, W24 scaffolded start, W25 dry-run and uninstall, W26 Windows handling, W27 `tools/` move, agent regeneration and self-attestation hook. Comes after waves 1 and 2 so it wraps already-hardened scripts instead of moving code that is about to change. Gate: CLI tests, old entry points still work with a hint.
6. **Wave 5: docs last (half a day).** W28 README quickstart with a real dashboard screenshot, W29 DECISION.md template, W30 `SECURITY.md`. Last because they describe the final commands and screens. Gate: every command in the README runs as written in a fresh repo.

If you only want the highest-value slice: waves 0 and 1, plus W12 and W18. That closes all three High findings and makes the verdict visible.
